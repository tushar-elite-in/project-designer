# Handling project source material

## Reference priority

Use this order unless the user states another:
1. The user's explicit instructions in the current conversation.
2. The supplied assignment or product brief, including marked mandatory constraints.
3. Existing project files and established conventions, when implementation context is supplied.
4. Wireframes, screenshots, examples, and supplementary documents for flow or presentation intent.
5. General recommendations, clearly labeled as recommendations.

A reference example can guide the level of detail and output format without becoming a requirement for every future project.

## Extract into categories

Record requirements under these labels:
- **Required:** explicitly mandatory, core, or needed for evaluation or operation.
- **Optional:** explicitly optional, recommended, or extra credit.
- **Assumption:** a reasonable choice needed to complete the plan but not stated by the source.
- **Open question:** missing or conflicting information that materially affects scope or design.

Capture, when present:
- Problem and intended outcome.
- User roles and permissions.
- Core and optional workflows/features.
- Technology mandates and prohibited choices.
- Data entities and fields.
- Validation, access control, and operational constraints.
- Required reports, demos, deployment, or submission format.
- Wireframe or visual guidance, including what is illustrative versus compulsory.

## Source traceability

For each major requirement, preserve a short source label or section name where possible. If exact page references are unavailable, cite the document title and heading. Do not fabricate citations or pretend to have read inaccessible pages.

When source material contains sample app links or inspiration, use them only for relevant patterns; do not copy their design or treat their behavior as a requirement without explicit direction.
